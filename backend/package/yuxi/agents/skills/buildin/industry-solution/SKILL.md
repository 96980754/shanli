# 多产品行业解决方案

仅在用户通过行业解决方案入口提交结构化请求，或明确要求基于多个产品资料生成行业解决方案时使用本技能。普通问答不要生成 Word。

## 工作流

1. 读取请求中的行业、需求和 `products` 数组。若 `products` 为空，从需求描述中识别用户明确提到的产品名称填入 `research_industry_products` 的 `products` 参数；只取需求中明确提到的产品，不得臆造或补全。若识别出的不同产品不足 2 个，先向用户询问需要哪几个产品，不要强行继续。
2. 调用 `list_kbs` 获取当前用户、当前会话可访问的知识库 ID。
3. 将全部可用 `kb_id`、行业、需求和原始产品数组一次传给 `research_industry_products`。
4. 该工具会对每个产品分别检索。只使用返回的 `products[].evidence`，不得用模型常识补写产品能力。
5. 综合生成一份结构化方案，至少包含：行业/场景需求、总体方案、各产品能力与角色、产品协同、实施思路、预期价值。
6. 正文引用只能使用工具返回的 `source_reference`，格式为 `[1]`、`[2]`；不得改变某条来源的产品归属。
7. 若任一产品没有足够证据，必须在方案中明确该产品资料不足，不得编造。
8. 将不含来源列表的最终 Markdown 正文、原始产品数组和工具返回的完整 `sources` 传给 `export_industry_solution_docx`。
9. 工具返回后：
   - 最终聊天正文必须原样使用 `chat_markdown`，保证 Chat 与 Word 的正文和引用一致；
   - 调用 `present_artifacts` 展示返回的 `file_path`，不要再次生成文档。

## 文档结构与格式规范（白皮书级）

生成的方案正文需遵循白皮书式的专业结构，按需包含以下章节（可合并或省略不适用项）：

1. **方案概述**：背景与目标、需求分析、范围界定。
2. **总体方案**：整体设计思路与目标架构。
3. **各产品能力与角色**：每个产品的能力定位与在方案中的角色；产品资料不足的须明确说明，不得编造。
4. **产品协同**：多产品如何配合形成完整能力。
5. **系统架构**：分层架构 / 拓扑 / 组件关系（适合用表格呈现）。
6. **实施思路**：部署、实施阶段划分、交付与运维建议。
7. **应用场景**：面向行业的具体应用场景与价值。
8. **预期价值**：可验证的收益，尽量量化。
9. **风险与应对**：潜在风险及应对措施。

格式要求：

- **标题层级**：一级章节用 `#`，二级用 `##`，层级不超过三级；章节标题带上编号（如「1. 总体概述」「1.1 文档说明」），使 Word 目录直接呈现清晰的章节树。
- **表格**：产品对比、架构分层、角色分工、实施阶段、指标对比等适合表格的信息，用 Markdown 表格呈现，表头加粗。
- **文风**：面向客户的正式商务文档，术语统一、避免口语和空泛表述；每条结论必须基于工具返回的证据并正确引用。

## 引用规则

- 产品 A 的结论只能引用产品 A 的 evidence/source。
- 正文出现的每个编号必须存在于最终“来源 / References”列表。
- 不得展示内部路径、数据库主键、对象存储地址或未由工具返回的元数据。
- 没有来源的结论不得写入方案。
