# 移动端适配（手机端不破版）

日期：2026-09-24
范围：`web/` 前端；不改后端、不改接口

## 目标

让平台在手机上（≤430px CSS 宽度）可用。当前已有半套移动端机制（`AppLayout` 的抽屉侧栏、部分页面的 768px 断点），但主链路仍有硬破版点，且**全项目没有一条 `@media` 以 430px/400px/375px 为断点**。

## 范围

| 范围 | 处理方式 |
|---|---|
| 主链路 4 页：登录 / 问答 / 知识库（列表+详情）/ 数据总览 | 完整适配，硬破版点全部修掉 |
| 其余 17 个管理页 | 只保证不横向溢出、不破版；不重排布局 |
| App 外壳（Capacitor） | 响应式为主，用安全区变量兜住状态栏/刘海/软键盘 |

**深度：最小可用。** 不做底部标签导航、不做列表卡片化——那是另一个量级的工作。

## 验收标准

直接采用 `docs/develop-guides/design.md` §8「响应式行为」，不另起一套：

1. 小屏下表单字段纵向排列，按钮组可换行
2. 侧栏、抽屉和弹窗要保证最小宽度内内容可读
3. 表格在小屏下允许横向滚动；不要把关键字段压缩到不可读
4. 图标按钮和主要操作需要保持可点击区域，移动端目标尺寸尽量不小于 40px

补充两条可验证的：

5. **在 430px 宽度下，任何页面都不出现横向滚动条**（表格自身的横向滚动除外）
6. **在 430px 宽度下，所有主操作按钮可见可点**（不允许被 `overflow: hidden` 裁掉）

### 横向溢出实测（补充执行）

Docker 起来后补做的。用 headless Chromium（playwright-core + 本机已缓存的 chromium，注入本地签发的测试 JWT 到 `localStorage.user_token` 绕过登录），在 **430 / 414 / 390 / 375 / 360 / 320** 六档宽度 × **工作台、数据总览、知识浏览、扩展、知识库详情、问答、问答明细、反馈列表、知识缺口、模型管理、登录** 11 个页面共 **66 个组合**上逐页量：

- `document.scrollingElement.scrollWidth > clientWidth`（文档级横向滚动）
- `#app-router-view.scrollWidth > clientWidth`（内容区横向滚动）
- 遍历 `#app-router-view *`，找右边界越出视口、且不在任何 `overflow-x: auto/scroll/hidden` 祖先内的元素

**结果：66 个组合全部为 0。** 验收项「430px 下无横向滚动条（表格自身横滚除外）」由按 CSS 推导变为实测结论。

**判定口径的补充（第二轮发现）**：这套「越界元素」判定对 antd 栅格负边距不敏感。`/knowledge-browser` 的 `.ant-row` 带 `margin: 0 -8px`（配合 `.ant-col` 的 `padding: 0 8px`），栅格盒左右各越出视口 8px，使 `#app-router-view` 的 `scrollWidth` 比 `clientWidth` 大 8px（390 → 398）。

- **文档级没有横滚**（`documentElement.scrollWidth === clientWidth === 390`），栅格内容右边界正好落在视口边（390），没有任何内容被裁切——所以这是一个只在内容区内部多出 8px 可滚余量的问题，不是破版。
- 用「暂存本次改动前后各测一次」确认**改动前后完全一致**，属既有问题，与本次无关，未处理。

### 一次被推翻的猜测（记录以免重蹈）

曾怀疑汉堡按钮（`.mobile-sidebar-trigger`，`position: fixed; z-index: 1000`）会被 `PageHeader`（`position: sticky; top: 0; z-index: 1000`，DOM 顺序在后故同层时绘制在上）盖住，进而怀疑 `.app-layout { height: 100dvh }` 与 `body { min-height: 100vh }` 不一致会让文档也滚动、把粘性头部拖进按钮区域。

实测均不成立：按钮矩形恒为 `[10, 10, 48, 48]`，`.app-topbar` 底边 48，`PageHeader` 从 48 起，三者严丝合缝不重叠；文档在六档宽度下均不可滚。`document.elementFromPoint` 打在按钮中心返回的就是按钮本身，六页皆然；`z-index ≥ 1000` 且与按钮矩形相交的元素，除 antd message 容器外一个都没有。

**故未做任何 z-index 改动。** 甲方反馈的「被盖住」后来确认是在 Chrome 手机模拟下看到的旧产物（热重载尚未吃到 `AppLayout` 那次改动），刷新后即正常。

## 第二轮：App 端「页面大于屏幕 + 双击放大」的根因（构建目标错配）

**反馈**：iPhone 上的 App 里，页面比屏幕高、能上下拖动；后续补充「上下左右都比手机屏幕大」，并且「会出现双击放大」。

**定位过程**：

1. 浏览器侧已实测干净（32 个组合里外壳与视口严丝合缝），所以问题只可能在 App 的 WKWebView 上。
2. 先排除「App 跑的是旧产物」：拉 `https://39.105.10.183/` 与它的入口 CSS，`viewport-fit=cover`、`--safe-top`、`height: 100dvh` 全都在，且产物 CSS 的哈希与本地构建 HEAD 得到的哈希一致——**App 跑的就是第一轮之后的代码**。
3. 于是把目光移到构建产物本身，发现两处**产物与源码不一致**的地方，再往上追就找到了真因。

**根因**：iOS 工程的部署目标与前端构建的浏览器基线对不上。

| 位置 | 声明 | 实际要求 |
|---|---|---|
| `web/ios/App/App.xcodeproj` | `IPHONEOS_DEPLOYMENT_TARGET = 15.0` | 设备可低至 iOS 15.0 |
| 产物 CSS 的 26 条断点 | `@media (width<=768px)` 等区间语法 | **iOS 16.4** 才支持 |
| 产物 CSS 的 `.app-layout` | `height: 100dvh`（`100vh` 回退被删） | **iOS 15.4** 才支持 `dvh` |

`vite.config.js` 从未约束 `build.target`，Vite 默认按 `baseline-widely-available` 压缩 CSS，于是压缩器把全部 `@media (max-width: …)` 改写成更短的 Media Queries L4 区间语法，并删掉了 `height: 100dvh` 之前那条 `height: 100vh` 回退（源码里两行都在，产物里只剩一行）。

| 设备 iOS | 26 条断点 | `height: 100dvh` | 表现 |
|---|---|---|---|
| 15.0~15.3 | 全部失效 | 不支持 → `.app-layout` 无高度 | 桌面布局 + 外壳塌陷，页面比屏幕高 |
| 15.4~16.3 | 全部失效 | 生效 | 桌面布局，宽高都超出屏幕、内容溢出故可缩放 |
| ≥16.4 | 正常 | 生效 | 正常 |

**为什么第一轮没发现**：本机复验用的是 headless Chromium，而 Chromium 自 104 就支持区间语法——**同一条 CSS，Chromium 正常、iOS 16.0~16.3 全废**。第一轮的 66 组合实测因此天然测不出这个错配。

**修法**：约束 CSS 目标，而不是改 26 处写法。

```js
// web/vite.config.js
build: { cssTarget: 'safari15' }
```

- 只设 `cssTarget` 不设 `build.target`：JS 产物不受影响，仅 CSS 压缩按 safari15 处理。
- 实测产物 73 个查询块里 `@media` 全部回到 `max-width` / `min-width`，`.app-layout` 恢复成 `height:100vh;height:100dvh` 两行。
- 代价是 esbuild 顺带补了 `-webkit-appearance`、`:-webkit-full-screen` 前缀并把重复选择器收进 `:is()`（Safari 14+ 均支持）；入口 CSS 104600 → 104802 字节。

**双击缩放是独立问题**，与断点无关：`index.html` 的 viewport 原本只有 `width=device-width, initial-scale=1.0`，既没有 `maximum-scale` 也没有 `user-scalable`。而 iOS 自 iOS 10 起对 Safari 就忽略 `user-scalable=no`，真正生效的是 CSS：

- `index.html` 补 `maximum-scale=1.0, user-scalable=no`（Android WebView 与部分场景直接生效）。
- `main.css` 增 `html { touch-action: pan-x pan-y }`——`touch-action` 沿祖先链取交集，挂 `html` 上即可覆盖整页，且不禁用滚动；`AgentPanel.vue` 原有的 `touch-action: none` 比它更严格，交集仍为 `none`，行为不变。

**踩坑记录**：`main.css` 是**纯 CSS**，注释只能用 `/* */`。多个组件的 `<style lang="less">` 会 `@import` 它，往里写 `//` 会被一并带进样式块，导致构建期 CSS 解析失败，而且报错指向的是某个 Vue 组件（`AgentChatComponent.vue`）而非 `main.css`，极易误判成 Vite 的问题。

**验证**：

- `pnpm run build` 通过；改动前后产物 CSS 逐选择器比对，差异仅「`app-layout` 恢复 `100vh` 回退」「加前缀」「`:is()` 收拢」三类。
- headless Chromium，4 组「尺寸 × 安全区」× 8 页 = **32 个组合**：外壳高度 === 视口高、内容区底边 === 视口底边、文档均不可滚、`touch-action` computed 为 `pan-x pan-y`。
- `eslint` / `check:i18n` / `test:frontend`（16/16 + versionIntent + voiceRecorder）全部通过。

**一处残留**：`FileTable.vue:1464` 的 `@container file-table (max-width: 480px)` 仍被压成 `(width<=480px)`——esbuild 对容器查询不按 target 决定写法。但 `@container` 本身要 iOS 16.0+，该规则在 iOS 15 上本来就整体失效，只有 iOS 16.0~16.3 会少一条 `display:none`（隐掉一个冗余操作按钮），不值得为它再加构建期改写。
