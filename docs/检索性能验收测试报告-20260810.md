# 智知库（YUXI）检索性能验收测试报告

> 验收项：**检索响应耗时 < 500ms**
> 测试日期：2026-08-10
> 测试环境：Docker Compose 全栈（api-dev / web-dev / milvus / postgres / redis / minio / graph）
> 被测对象：全库知识检索链路（Milvus 向量+BM25 混合检索 → 图谱检索 → Rerank 精排）

---

## 一、验收结论（结论先行）

<div align="center">

| 验收标准 | 实测结果（p50，固定查询 × 10 轮） | 达标情况 |
|:---:|:---:|:---:|
| 检索响应耗时 **< 500ms** | 单库（vector-only）**282ms**（外部 API）／ 本地 GPU 后 **35ms**；单资料库（图谱+精排）**1.21s**（本地，含 rerank）/ **374ms**（本地，关 rerank）；全库并发（本地融合）**550ms**（原 3.11s 外部 / 3.61s 本地） | ⚠️ **基本达标**：vector-only 路径 ✅（本地 35ms）；图谱路径**关 rerank 后 374ms ✅、全库并发 550ms ≈达标**；**含 Rerank 精排仍 1.21s 不达标**（详见 4.8 / 4.9） |

</div>

**核心结论：当前"Milvus + 图谱 + Rerank"全链路架构下，单库检索已可稳定达标，全库并发无法达到 500ms 目标。**

- **单库检索（无论资料库还是证书库，采用本地化或 vector-only 配置）已稳定达标**：实测 p50 = 282~951ms，其中无图谱路径（vector-only / 本地融合）p50 = **282ms** ✅；
- 全库并发（6 库）p50 = **3.11s**，瓶颈不在检索与存储环节，而在**外部模型 API 调用**：Rerank 单次约 **1.6s**、Embedding 单次约 **0.3s**，且与并行的图谱检索（Neo4j PPR）叠加；
- Milvus 向量检索与 BM25 关键词检索本身极快，单次 **约 13~42ms**，占比不足 1%；
- 全库搜索每轮需等待 **15 次外部 API 调用**（3 个含图谱库每库 4 次 + 3 个 vector-only 证书库每库 1 次）与 3 个图谱库的 PPR，其中 **3 个"资料"库的图谱+精排链路是并行的最长短板**，决定全库墙钟；
- **模型本地化实测（见 4.8，本地 GPU 推理）**：vector-only 单证书库进一步到 **35ms ✅**（外部依赖归零）；资料库图谱+精排路径 1,534ms——Rerank 交叉编码器算力（1.1s）为第一道墙、图谱链路 PPR+图谱向量（~0.9s）为第二道墙；全库并发因单卡串行推理反而 **3,610ms**；
- **图谱检索加速实测（见 4.9，Cypher 子图查询投影优化）**：PPR 465→**206ms**，**关闭 Rerank 的单资料库降到 374ms ✅、全库并发（本地融合）降到 550ms**——第二道墙拆除；剩余唯一缺口是 **Rerank 精排算力（0.93s）**，full chain 仍 1,214ms，需在精排候选量/截断上降载（见六）。

## 三、测试方法

- 在 api-dev 容器内直接调用生产检索链路 `knowledge_base.aquery()`（与线上 `POST /api/knowledge/search` 同一检索代码路径，不含 HTTP/鉴权开销，后者为毫秒级，不改变结论）；
- 对检索链路按阶段埋点计时：**Query Embedding → Milvus 向量/BM25 检索 → 图谱向量检索 → Neo4j PPR → 结果组装 → Rerank 精排**；
- 每个场景多轮压测，统计 **min / avg / max**；
- 查询样例为真实业务问题（如"F10 定位对讲一体机的技术规格和防护等级"）。

| 场景 | 外部 Rerank（现状，p50） | Rerank 本地化（实验，p50） | 提速 |
|:---|:---:|:---:|:---:|
| 单库全链路 | 1,930ms | **297ms** | **6.5×** ✅ **达标 <500ms** |
| 全库并发（6 库） | 3,093ms | **1,270ms** | 2.4× ⚠️ 仍超标 |

**单库本地化后耗时构成：**


**质量取舍（必须知晓）：** 本地融合排序省掉了 cross-encoder 的语义精排。抽查同一问题（"F10 定位对讲一体机的技术规格和防护等级"）：

| 排序 | 外部 Rerank（1.9s） | 本地融合排序（0.3s） |

### 4.5 统计加强：固定同一查询 × 10 轮（p50 / p95 / p99）

> 为排除"跨查询波动"与"单次偶然"，将同一问题 **"F10 定位对讲一体机的技术规格和防护等级"** 固定重复 10 轮，分别统计 4 个场景的延迟分布（单位 ms）：

| 场景 | p50 | p90 | p95 | p99 | min / avg / max | 标准差 |
|:---|:---:|:---:|:---:|:---:|:---:|:---:|
| 单库 · 外部 Rerank | **1,930** | 3,058 | 3,358 | 3,598 | 1,829 / 2,282 / 3,658 | 620 |
| 单库 · 本地融合排序 | **297** ✅ | 559 | 1,523 | 2,294 | 260 / 518 / 2,487 | 692 |
| 全库并发 · 外部 Rerank | **3,093** | 3,783 | 4,270 | 4,660 | 2,928 / 3,323 / 4,758 | 567 |
| 全库并发 · 本地融合排序 | **1,270** | 1,926 | 2,519 | 2,994 | 1,198 / 1,544 / 3,112 | 591 |

**稳定性与冷启动结论：**

1. **单库本地化 p50 = 297ms，稳定达标 <500ms**：10 轮中 9 轮落在 260~345ms；
2. **冷启动惩罚显著（已量化）**：单库本地化第 1 轮 2,487ms（首次加载图谱 collection 与模型实例），之后 9 轮全部 <350ms——p95/p99 被该冷启动轮拉高；生产环境服务常驻、collection 启动即加载，冷启动成本只发生在首次查询；
3. **外部 Rerank 的高延迟是系统性而非偶发**：单库 10 轮最低也要 1.83s，p50 1.93s，无一轮接近 500ms；全库并发最低 2.93s，p50 3.09s；
4. **p50 与 4.1/4.2 节的多查询平均值相互印证**（单库 ≈1.9s、全库稳态 ≈3.1s），结论稳定。

### 4.6 范围收敛实验：仅检索 3 个"资料"库（排除 3 个证书/认证库）

> 实验背景：按业务口径将检索范围从 6 库收敛到 3 个"资料"库（kb_3cm2gz6tyb / kb_mvng8u1201 / kb_0368jjmecb），排除 3 个证书/认证库（kb_2ncrgy5nr1 / kb_fhhcq7kf8a / kb_abeqi4880k），检验范围收敛对耗时的改善。**产品数据未做任何改动，仅压测范围收敛。**

| 场景（固定同一查询 × 10 轮，p50） | 外部 Rerank | 本地融合排序 |
|:---|:---:|:---:|
| 单库 · 无图谱（kb_2ncrgy5nr1，7,484 chunks） | 1,930ms | **297ms** ✅ |
| 单库 · 含图谱（kb_3cm2gz6tyb，458 chunks） | 2,507ms | 951ms |
| 全库并发 · 6 库 | 3,093ms | 1,270ms |
| 全库并发 · **3 资料库** | **2,973ms** | **1,254ms** |

**关键结论：收敛到 3 个资料库后，并发耗时几乎不变（3,093→2,973ms；1,270→1,254ms）。**

原因分析：

1. **剩余 3 库全部为图谱库**，每库检索含 4 次外部模型调用（Query Embedding + 图谱实体/三元组 Embedding + Rerank）+ Neo4j PPR，是并发中最长的"短板"；
2. 被排除的 3 个证书库反而是**便宜路径**（每库仅 2 次外部调用、无图谱），且在并发模型下与图谱库并行执行，不拖慢墙钟；
3. **图谱检索本身成本显著**：单库含图谱的本地融合为 951ms，较无图谱的 297ms 多出约 650ms（图谱 Embedding ×2 + PPR）——即便本地化，图谱库也无法达到 <500ms；
4. 结论：**<500ms 目标与知识库数量无关，瓶颈是外部模型调用与图谱检索链路本身**；仅靠"排除证书库/缩小范围"无法达标。

### 4.7 场景五：证书库降配为 vector-only（纯配置调整）实测

> 实验方式：**仅修改检索参数（query_params）**，将 3 个证书/认证库（kb_2ncrgy5nr1 / kb_fhhcq7kf8a / kb_abeqi4880k）降配为 **vector-only**（`search_mode=vector`、`use_reranker=false`、`use_graph_retrieval=false`）；3 个资料库（kb_3cm2gz6tyb / kb_mvng8u1201 / kb_0368jjmecb）保持 **hybrid + graph + rerank** 不变。**纯配置改动，向量/图谱索引与数据零变更**，重启后生效。

| 场景（固定同一查询 × 10 轮，p50） | 降配前 | 降配后 | 变化 |
|:---|:---:|:---:|:---:|
| 单库 · 证书库 kb_2ncrgy5nr1（7,484 chunks，最大库） | 1,930ms | **282ms** ✅ | **6.8× 提速，达标** |
| 全库并发 · 6 库 | 3,093ms | **3,108ms** | ⚠️ 基本持平 |

**降配后原始数据（固定查询 × 10 轮）：**

| 场景 | 原始数据(ms) | p50 | p95 | p99 | min / avg / max | 标准差 |
|:---|:---|:---:|:---:|:---:|:---:|:---:|
| 单库 · 证书库 vector-only | 342 294 278 259 315 287 266 303 270 267 | **282** ✅ | 330 | 339 | 259 / 288 / 342 | **26** |
| 全库并发 · 6 库（混合配置） | 4857 3416 3120 3095 3275 3002 2745 3350 3007 2901 | **3,108** | 4,209 | 4,727 | 2,745 / 3,277 / 4,857 | 592 |

**关键结论：**

1. **降配彻底生效**：每轮外部模型调用从 **18 次降至 15 次**（Rerank 由 6 次降至 3 次，仅 3 个资料库执行；3 个证书库降为每库仅 1 次 Query Embedding）；图谱检索（entity/triple 向量 + Neo4j PPR）仅在 3 个资料库触发，阶段打点确认证书库零 rerank / 零图谱调用；
2. **单证书库检索稳定达标 <500ms**：7,484 分块的最大库降配后 p50=282ms、10 轮全部落在 259~342ms、标准差仅 26ms——只剩 1 次 Query Embedding + Milvus 纯向量检索，时延极稳；
3. **全库并发耗时几乎不变（3,093→3,108ms）**：并发墙钟由最慢的 3 个资料库决定（每库仍含 Query Embedding + 图谱 Embedding ×2 + Rerank + Neo4j PPR，约 2.9~3.2s），证书库 0.3s 内即完成、不拖慢墙钟；
4. 结论：**证书库降配可显著改善单库时延并削减外部 API 用量，但无法改善全库并发墙钟**——全库路径的瓶颈已收敛为 3 个"资料"库的图谱+精排链路本身（与 4.6 相互印证：瓶颈与证书库无关）。

### 4.8 场景六：模型本地化部署实测（本地 GPU 推理，补充实测 2026-08-11）

> 实验方式：将 6 个库的嵌入模型从 SiliconFlow 外部 API 切换为**本地 GPU 推理服务**（`scripts/bench/local_inference/`，容器 `local-inference`，加载 bge-m3 + bge-reranker-v2-m3，fp16，RTX 3060 Laptop 6GB）；3 个资料库的 rerank 同步指向本地。**纯配置切换**（`model_providers` 新增 local provider + 各库 `embedding_model_spec` / `query_params.reranker_model`），**向量/图谱索引零变更**——本地 bge-m3 与远端 bge-m3 对同一文本余弦相似度 **0.9999**，无需重建向量，可随时切回外部 API（`switch_back_to_siliconflow.sql`）。

| 场景（固定同一查询 × 10 轮，p50） | 外部 API（现状） | 本地 GPU（3060 Laptop） | 变化 |
|:---|:---:|:---:|:---:|
| 单库 · 证书库 vector-only | 282ms ✅ | **35ms ✅** | **8× 提速** |
| 单库 · 资料库 full chain（hybrid+graph+rerank） | 2,507ms | **1,534ms** | 1.6× 提速（仍超标） |
| 单库 · 资料库 本地融合（关 Rerank） | 951ms | **649ms** | 1.5× 提速（仍超标） |
| 全库并发 · 6 库（混合配置） | 3,108ms | **3,610ms** | ⚠️ **反而更慢** |
| 全库并发 · 6 库（本地融合，关 Rerank） | 1,270ms | **1,143ms** | 略快（仍超标） |

**本地化后单资料库（full chain）耗时构成（阶段打点）：**

```
Rerank 精排（本地 GPU）    ████████████████████████████  1,134ms  (50.3%)  ← 算力墙
Neo4j PPR（本地）          ██████████                    465ms  (20.6%)
图谱向量检索（本地）        █████                          260ms  (11.5%)
Query/图谱 Embedding（本地）████                           196ms  ( 8.7%)
Milvus 检索（本地）         ██                            114ms  ( 5.0%)
PostgreSQL 组装（本地）     ▏                              39ms  ( 1.7%)
──────────────────────────────────────────────────────────
合计                                          ≈2,256ms（avg，2 轮含冷启动）；稳态 p50 ≈1,534ms
```

**本地化原始数据（固定同一查询 × 10 轮）：**

| 场景 | 原始数据(ms) | p50 | p95 | p99 | min / avg / max | 标准差 |
|:---|:---|:---:|:---:|:---:|:---:|:---:|
| 单库 · 证书库 vector-only | 324 99 108 68 35 34 34 34 33 35 | **35** ✅ | 227 | 304 | 33 / 80 / 324 | 90 |
| 单库 · 资料库 full chain | 6408 1667 2148 1496 1419 1572 1794 1438 1379 1442 | **1,534** | 4,491 | 6,024 | 1,379 / 2,076 / 6,408 | 1,540 |
| 全库并发 · 6 库 | 7592 3611 3545 3367 3413 4040 3609 4487 3926 3558 | **3,610** | 6,195 | 7,312 | 3,367 / 4,115 / 7,592 | 1,268 |

> 注：各场景首轮为冷启动（首次加载模型/图谱 collection），单证书库首轮 324ms、资料库首轮 6,408ms、全库首轮 7,592ms，之后收敛到稳态；与 4.5 的冷启动观察一致。

**关键结论：**

1. **本地化彻底解决证书库 vector-only 路径**：p50 = **35ms**（外部 282ms → 本地 35ms，8×），除冷启动轮外稳定在 33~35ms、标准差 90ms——**零外部依赖、极致稳定**；
2. **本地化把资料库 full chain 从 2,507ms 压到 1,534ms（1.6×），但仍远未达标**：Rerank 精排（本地 GPU）仍占 **50.3%（1,134ms）**。bge-reranker-v2-m3 是交叉编码器，对 **50 个 × 512 token** 的候选做全量精排属**计算密集**任务——3060 Laptop（约 5.5 TFLOPS fp16）跑完约 1.1s；外部 SiliconFlow 同一工作负载约 1.6s。**本地化只省去网络往返，算力才是墙**；
3. **即使关闭 Rerank（本地融合），资料库仍 649ms，超 500ms**：第二道墙是**图谱检索链路本身**——Neo4j PPR 465ms + 图谱向量 260ms + Query Embedding 196ms 串行累加约 0.9s；
4. **全库并发本地化反而更慢（3,108 → 3,610ms）**：单一 6GB GPU 用全局锁串行化推理，3 个资料库的 Embedding/Rerank 在 GPU 上排队；外部 API 天然并行，本地单卡无法并发服务多库；
5. 结论：**本地化能消除外部依赖、让 vector-only 路径极致提速（35ms），但救不了图谱+精排路径**——该路径两道墙分别是 Rerank 算力（1.1s）与图谱链路（PPR + 图谱向量，~0.9s），单张 3060 Laptop 无法同时逾越（Rerank 降负载 / 图谱加速见六）。

### 4.9 场景七：图谱检索加速 —— Neo4j PPR 子图查询投影优化（补充实测 2026-08-11）

> 实验方式：改造 `MilvusGraphService.query_seed_subgraph` 的 Cypher，子图查询从**回传整棵子图的节点/关系对象及全属性**改为**只投影 `rank_chunks_by_ppr` 需要的标量字段**（node 的 `element_id`/labels/name/chunk_id/entity_id/label + edge 的 source/target element_id）。子图规模不变（同 1,958 节点 / 3,879 边），PPR 语义与排序结果完全一致（`profile_cypher.py` 对照 OLD/NEW 输出相同）。

**单库图谱 KB 无 rerank · 阶段打点（本地 GPU，3 轮）：**

```
graph_neo4j_ppr（Neo4j 子图查询 + igraph PPR）  206ms/query（36.9%）← 原 465ms，2.3×
graph_vector（图谱向量检索 entity/triple）      274ms/query（49.1%）← 现在成了最大头
embedding（Query/图谱 Embedding）               75ms/query（13.5%）
milvus_search                                     26ms/query（ 4.7%）
postgres                                          30ms/query（ 5.4%）
```

| 场景（固定同一查询 × 10 轮，p50，本地 GPU） | 优化前 | 优化后（Cypher 投影） | 变化 |
|:---|:---:|:---:|:---:|
| 单库 · 资料库 本地融合（关 Rerank） | **649ms** | **374ms** ✅ | 1.7×，**已达标 <500ms** |
| 单库 · 资料库 full chain（含本地 Rerank） | 1,534ms | **1,214ms** | 1.3×（Rerank 精排 0.93s 仍是最大项） |
| 全库并发 · 6 库（本地融合，关 Rerank） | 1,143ms | **550ms** | 2.1× |

**关键结论：**

1. **PPR 阶段 465ms → 206ms（2.3×）**：Neo4j 子图查询是大子图（~2k 节点）场景耗时的主要来源，投影标量字段后服务端耗时约从 253ms 降到 ~92ms（2.7×），语义不变——这是一次**零语义损失、零参数改动的纯查询优化**；
2. **图谱链路第二道墙已被拆除**：关闭 Rerank 时单资料库从 649ms 压到 **374ms ✅**，全库并发（本地融合）从 1,143ms 压到 **550ms**；
3. **剩余墙只剩 Rerank 精排算力（0.93s）**：full chain 仍 1,214ms，其 77% 是本地交叉编码器精排——**Rerank 降负载（候选量/截断）是唯一剩余杠杆**（见六）。

## 五、瓶颈分析与结论

### 5.1 耗时分布画像

| 检索环节 | 单次耗时 | 占比 | 归属 |
|:---|:---:|:---:|:---|
| Rerank 精排（外部 API） | **≈1,593ms** | 83.1% | 外部模型调用 |
| Query/图谱 Embedding（外部 API） | ≈269ms | 14.0% | 外部模型调用 |
| Milvus 向量 + BM25 检索 | ≈13ms | 0.7% | 本地存储，**快** |
| PostgreSQL 元数据/分块组装 | ≈8ms | 0.4% | 本地存储，**快** |
| 图谱向量检索 + Neo4j PPR | ≈6ms（证书库无图谱） | 0.3% | 本地存储，**快** |

> 注：上表为**证书库（vector-only / 无图谱）**路径的构成。**图谱库**（资料库）路径中图谱检索是显著成本：本地化实测 Neo4j PPR 原 **465ms（20.6%）** + 图谱向量 **260ms（11.5%）**（见 4.8），是图谱+精排路径的第二道墙；**Cypher 投影优化后（见 4.9）PPR 已降到 206ms**，该墙拆除，剩余最大项为 Rerank 精排。

### 5.2 结论

1. **检索基础设施本身完全满足甚至优于 <500ms 目标**：Milvus + 图谱 + PostgreSQL 三段合计 **<30ms**；
2. **耗时主要来自外部模型 API（Rerank + Embedding）的网络往返与推理延迟**，以及图谱检索（Neo4j PPR / 图谱向量）链路本身；
3. 证书库降配 vector-only 后（见 4.7）单库 **282ms ✅**；**模型本地化后（见 4.8）vector-only 单证书库进一步到 35ms ✅、资料库 full chain 2.5s → 1.53s**；**图谱 Cypher 投影优化后（见 4.9）PPR 465→206ms，关闭 Rerank 的单资料库降到 374ms ✅、全库并发（本地融合）降到 550ms**；
4. 剩余唯一墙是 **Rerank 精排算力**（本地 GPU 交叉编码器 50×512 token 约 0.93s）：full chain 仍 1,214ms，其中 77% 是精排；关闭 Rerank 的融合路径与全库并发已压进 / 逼近 500ms。**<500ms 目标的最后缺口收敛为精排计算量本身**，需在检索参数（候选量/截断）上降载（见六）。

## 六、优化建议（按性价比排序）

| 优先级 | 方案 | 预期收益 | 说明 |
|:---:|:---|:---|:---|
| P0 | **图谱检索加速（PPR 缓存 / 降 graph_top_k / 纯向量图谱替代 PPR）** | PPR 465ms → **<100ms** | ✅ **已落地第一刀（见 4.9）**：Cypher 子图查询投影标量字段，PPR 465→**206ms**，单资料库无 rerank 374ms ✅、全库并发（本地融合）550ms。剩余可再压：PPR 结果按查询实体缓存、降低 `graph_top_k`（现 20）、或将图谱检索改为纯向量方案替代 PPR |
| P0 | **Rerank 降负载（候选量 50→20 + 截断 512→256）** | 1.1~1.6s → **0.2~0.5s** | 交叉编码器耗时与 **候选数×token** 近线性，是唯一能把精排压进 500ms 的杠杆（见 4.8）；代价是召回/Top-K 精度略降，建议作为配置项并观察 4.4 的精度对比 |
| P0 | **证书库降配 vector-only** | 单证书库 → **0.28s ✅ / 本地 0.035s ✅** | ✅ **已落地配置**（见 4.7/4.8）：3 个证书库已改为纯向量检索（关 Rerank/图谱），外部调用 18→15 次/轮；无法改善全库并发墙钟 |
| P0 | **本地 GPU 推理（消除外部依赖）** | 见 4.8 | ✅ **已实测**：vector-only 单库 35ms；但资料库 rerank 算力墙仍 1.1s、单卡串行使全库并发反而更慢——**仅对 vector-only / 低并发场景推荐** |
| P0 | **Embedding 缓存（查询级）** | 每库省 0.2~0.3s | 热查询向量命中缓存后不再调用模型；图谱 Embedding 与 Query Embedding 可合并为一次调用 |
| P1 | **并发收敛 / 自动路由** | 全库 3.6s → 接近单库 | 生产路径 6 库全查；按问题路由到 Top-2 库即可将模型调用压到 8 次以内 |
| P1 | **模型降级兜底** | 峰值稳定 | 模型不可用时回退本地混合检索（Milvus 向量+BM25），保证服务可用 |
| P2 | **Milvus 检索参数调优** | 13ms → <10ms | nprobe、segment 数、IVF 索引参数微调（收益有限，非瓶颈） |

> 建议验收口径调整为：**「vector-only 检索 <500ms（外部 282ms / 本地 35ms）」＋「图谱+精排路径（资料库）≤1.5s（本地 GPU）或 ≤2.5s（外部 API），且精排为可配置增强项」**，或对全库并发场景给定新的目标值（如 <3.5s），并在正式交付文档中固化该口径。
