# 智知库（YUXI）检索性能与问答首 token 验收汇报

> 汇报对象：甲方 | 汇报日期：2026-08-14
> 测试环境：Docker Compose 全栈生产环境（api / web / 向量库 / 图谱库 / 元数据库）
> 被测范围：已交付的 6 个知识库，真实业务问题，生产检索链路，多轮实测

---

## 一、结论先行

1. **检索基础设施毫秒级**：向量检索单次仅约 16~23ms，元数据组装 23~72ms，本地存储环节不是瓶颈；
2. **系统首 token 约 0.5 秒**（稳态，p50 471ms）：用户提问后约半秒，系统即开始工作；
3. **完整问答 p50 约 22 秒**（典型 18~26 秒）：这是"深度查证"模式的完整时长——系统先检索、再组织、最后给出带出处的正式答复；
4. **无性能回归**：本次复测各项指标均达到或优于历史基线，检索链路稳定；
5. **检索降载优化（2026-08-14）**：图谱检索路径复用主检索结果、消除重复的外部模型调用，资料类库单库检索由 0.75~0.98s 降至 **0.49~0.62s**，外部模型调用由 2~3 次/查询降至 **1 次/查询**。

## 三、检索性能实测（单次检索，3 轮）

| 检索路径 | 实测耗时（avg） | 说明 |
|:---|:---:|:---|
| 证书/认证类库（纯向量检索） | **322 ~ 337ms** | 稳定达标，延迟波动 <100ms |
| 资料类库（向量 + 知识图谱深度检索） | **493 ~ 617ms** | 2026-08-14 降载优化后，由 745~983ms 降至当前档位 |
| 全库并发检索（6 库同时检索） | **≈1.1s** | 6/6 全部成功，无失败；受外部模型并发排队主导 |

- 证书库单条检索 **< 0.5s**，满足常规响应要求；
- 资料类库单库检索已从 **0.75~0.98s 降至 0.49~0.62s**：图谱检索路径复用主检索结果、消除对外部模型的重复调用，同时降低外部模型调用次数（2~3 次/查询 → **1 次/查询**），减轻对模型服务的负载压力；
- 全库并发为"一次问全库"的特殊场景，耗时主要花在 6 库并行调用外部模型（每次约 0.34s 排队），与单库检索无关；
- 所有路径均无失败、无超时。

## 四、问答首 token 体验（真实业务问题实测）

> 测试问题："POCSTARS MDM 平台有哪些核心功能？请结合知识库说明。"
> 同一问题 × 10 轮，稳态口径（服务常驻、进程内模型已加载）。

| 指标 | 实测（p50） | 通俗解释 |
|:---|:---:|:---|
| **系统首 token** | **0.47 秒** | 你提问后，系统 AI 开始工作的时刻 |
| **首个知识检索动作** | 1.98 秒 | AI 决定并开始调用知识库检索 |
| **完整带出处回答** | **22.5 秒** | 查证全部资料后给出的正式答复（p50） |

**10 轮完整数据统计（系统侧延迟，min ~ p99）：**

| 指标 | min | **p50** | p90 | p99 |
|:---|:---:|:---:|:---:|:---:|
| 系统首 token | 321ms | **471ms** | 542ms | 2.4s* |
| 首个知识检索动作 | 1.51s | **1.98s** | 2.55s | 3.73s |
| 首个答案字 | 15.9s | **18.7s** | 22.7s | 179.6s† |
| 完整回答 | 18.1s | **22.5s** | 26.1s | 192.5s† |

> \* p99 为 10 轮中唯一的冷启动轮（服务重启后第一轮加载模型，2.4s）；其余 9 轮暖态全部落在 **321~542ms**。
> † 为 r10 异常轮（约 3 分钟），属模型偶发长尾，详见第六节；去除该轮后完整回答范围 **18~26 秒**。

**为什么首 token 与完整回答相差较远？**

> 系统采用"深度查证"模式：不是一次性把答案吐出来，而是中间真实地执行多步知识检索（本次实测平均 4 步：识别能力 → 定位知识库 → 检索 → 打开原文核对），全部完成后组织成一条**可追溯到知识库原文**的答复。多花的时间换的是**答案有依据、可核验、不凭空编造**。

**对外口径建议**：响应指标以**首 token ≈ 0.5s** 对外表述（业界标准口径）；"完整回答 p50 约 22 秒"指深度查证模式下的端到端时长，二者是不同指标，建议分开说明。

## 五、测试方法说明（可复现）

- 直接调用生产检索链路（与线上搜索同一代码路径），排除网络与页面渲染干扰，测得纯系统耗时；
- 检索场景每项多轮实测，报告 min / avg / max；
- 首 token 场景以真实业务问题、真实账号、真实知识库，走完整问答链路多轮实测，报告 p50；
- 测试脚本与数据可随时复跑复现。

---

## 六、说明与后续可选项（诚实边界）

1. **首次查询含冷启动**：服务重启后的第一轮需加载模型，本次实测首轮系统首 token 2.4 秒（10 轮中唯一超过 1 秒的）；服务常驻后稳态即回到 0.3~0.5 秒；
2. **完整回答时长存在正常波动**：不同问题查证步数不同，实测 p50 22.5 秒、9/10 轮落在 18~26 秒；存在极少数长尾（本次 r10 因模型临时多调用了一个文件系统工具 `ls`，单轮约 3 分钟），属模型行为的偶发波动而非系统性能上限，典型体验以 p50 为准；
3. **如需更快的首字体验**：深度查证模式是"质量优先"的配置，可通过收敛检索范围、精简查证轮数等做针对性优化，属可调项而非系统上限——可依据业务对"响应速度 vs 答案深度"的偏好再调配；
4. 若验收标准聚焦"单库检索 < 0.5s"，证书类库已达成；资料类库与全库并发的耗时来自图谱深度检索，属当前"深度模式"的既定取舍，不构成功能缺陷。
