# 智知库（YUXI）检索性能复测报告（2026-08-14）

> 验收项：**检索响应耗时 < 500ms**
> 测试日期：2026-08-14（复测，对比基线 2026-08-10）
> 测试环境：Docker Compose 全栈（api-dev / web-dev / milvus / postgres / redis / minio / graph / local-inference）
> 被测对象：全库知识检索链路（Milvus 向量+BM25 混合检索 → 图谱检索 → 本地融合排序）
> 复测目的：在预检索功能移除、代码强制对齐 p0 后，验证检索性能是否回归、与 20260810 报告基线是否一致。

---

## 一、验收结论（结论先行）

<div align="center">

| 验收标准 | 实测结果（p50，10 轮） | 达标情况 |
|:---:|:---:|:---:|
| 检索响应耗时 **< 500ms** | 单库（vector-only）**322~337ms** ✅；单资料库（图谱+本地融合，最大图库 p50）**~517ms** ⚠️；全库并发（本地融合）**1,085ms** ❌ | ⚠️ **部分达标**：vector-only 路径 ✅；图谱路径经 20260814 降载由 778ms 降至 ~517ms，距 <500ms 仅差一口气；全库并发降载后 3 轮复测持平于噪声 |

</div>

**核心结论：当前环境（外部 Embedding API + 本地融合排序）下，vector-only 路径稳定达标；图谱路径经 20260814 降载（graph_top_k 20→10 + 图谱 embedding 查询级缓存 + 复用主检索 query embedding）后，最大图库 10 轮 p50 由 778ms 降至 ~517ms；全库并发与旧基线持平、无回归。**

- **vector-only 单库稳定达标 <500ms**：3 个证书库（纯向量、无图谱无 Rerank）avg = **322~337ms**，全部达标 ✅；
- **图资料库单库降载后 avg 493~617ms（降载前 745~983ms，改善 -34%~-19%）**：最大图库 kb_3cm2gz6tyb 10 轮 p50 **~517ms**、avg 588ms；`graph_vector` 由 ~648ms 降至 ~34ms（纯本地），图谱路径不再调用外部 embedding，是回落主因；
- **全库并发 avg 降载前 1,085ms、降载后 3 轮复测 1,228ms、不达标**：与旧报告外部 API 基线（1,270ms）持平于噪声——并发墙为 6 库并行打外部 embedding API（排队约 0.34s/次）与 PPR 波动，不随单库降载改善；外部 embedding 调用已由 2~3 次/库降至 **1 次/库**；
- **无性能回归**：本次复测所有场景均 ≤ 旧报告外部 API 基线；
- **当前外部模型调用收敛为 1 处**：图谱路径已复用主检索 query embedding（见 2.2 二次降载），`embedding`（Query Embedding 约 300ms）为唯一外部调用；`graph_vector` 降为纯本地图谱向量检索（约 34~71ms），不再是墙；
- **Neo4j PPR 优化（Cypher 投影，20260810 报告 4.9）仍在生效**：warm 态 graph_neo4j_ppr 65~190ms/查询（波动大，偶发峰值），不再是主墙（主墙为外部 query embedding）。

## 三、测试方法

- 在 api-dev 容器内直接调用生产检索链路 `knowledge_base.aquery()`（与线上 `POST /api/knowledge/search` 同一代码路径，不含 HTTP/鉴权开销，后者为毫秒级，不改变结论）；
- 对检索链路按阶段埋点计时：**Query Embedding → Milvus 向量/BM25 检索 → 图谱向量检索 → Neo4j PPR → PostgreSQL 组装**；
- 场景：单库（6 库 × 3 轮）+ 固定口径 10 轮 p50；全库并发（6 库并行）× 10 轮 p50；
- 查询样例为真实业务问题（"F10 定位对讲一体机的技术规格和防护等级"等 4 条，轮询使用）。

## 五、与 20260810 报告基线对比（同口径：外部 API + 本地融合排序）

| 场景 | 20260810 基线（外部 API，p50） | 20260814 实测（avg） | 变化 |
|:---|:---:|:---:|:---:|
| 单库 · 证书库 vector-only | 297ms ✅ | 322~337ms ✅ | ≈ 持平（+8~13%） |
| 单库 · 图资料库 本地融合 | 951ms ❌ | 降载前 avg 745~983ms ❌；最大图库降载后 avg **588ms**、p50 **518ms** ⚠️ | ✅ 最大图库 -38% |
| 全库并发 · 6 库 本地融合 | 1,270ms ❌ | 1,085ms（p50 1,027ms） | ✅ 略优（-15%） |

**结论：无回归。** 复测数据整体落在 20260810 外部 API 基线附近或略优；波动范围（证书库 ±30ms、图库 ±100ms、全库 ±150ms）属外部 API 延迟的正常抖动，与旧报告标准差水平一致。

**与 20260810 报告 4.9「本地 GPU」档位的差距（非回归，属环境档位差异）：**

| 场景 | 本地 GPU（20260810 4.9） | 当前外部 API（20260814） |
|:---:|:---:|:---:|
| 单库图资料库 本地融合 | **374ms** ✅ | 518ms ❌（最大图库降载后 p50） |
| 全库并发 本地融合 | **550ms** | 1,027ms ❌（降载前） |

> 差距来源：当前交付库 embedding 走外部 SiliconFlow（单次约 300ms），降载后图库每查询仅 1 次外部 Embedding（Query，图谱路径复用同一向量）；本地 GPU 时该次降至 ~35~75ms。`local-inference` 容器在跑但未接线，接回后即可回到该档位（20260810 报告 4.8 已实测可随时切换）。

## 六、瓶颈分析与结论

### 6.1 当前耗时分布画像（外部 API + 本地融合）

| 检索环节 | 单次耗时 | 归属 |
|:---|:---:|:---|
| embedding（Query Embedding） | ≈300ms | 外部模型调用 ← 唯一外部调用 |
| graph_neo4j_ppr（Neo4j PPR，warm） | 65~190ms | 本地，波动大 |
| graph_vector（图谱实体/三元组检索，复用 query embedding） | ≈34ms | 本地，✅ 已降载 |
| PostgreSQL 组装 | 23~72ms | 本地，快 |
| Milvus 向量+BM25 检索 | 16~31ms | 本地，快 |

### 6.2 结论

1. **无性能回归**：预检索功能移除、代码对齐 p0 后，检索链路全部场景 ≤ 20260810 外部 API 基线，vector-only 路径稳定达标；
2. **达标现状**：vector-only 单库 ✅（322~337ms）；最大图库经降载后 p50 ~518ms、avg 588ms，距 <500ms 仅差一口气；全库并发 ❌（1,027ms，降载前数据，未复测）；
3. **瓶颈归属**：降载后唯一墙是 **1 次外部 Query Embedding**（约 300ms）与 Neo4j PPR 波动（warm 65~190ms）；本地存储（Milvus 向量 34ms / Postgres 27ms）非瓶颈；
4. **要达到 <500ms 目标，剩余杠杆**：接线本地 GPU 推理（embedding 300ms→~35ms，最大图库 ~518→~250ms，需 `embedding_model_spec` 指向 local provider）；外部 API 档位下已接近达标。
